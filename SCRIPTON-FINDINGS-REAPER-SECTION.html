71 — Eighteen runs that were never running

A ledger that can open a row but not close it will fill with rows that mean nothing

AiRun rows are opened at RUNNING by begin() and closed by finish() or fail(). When the process dies mid-call neither runs. Eighteen such rows had accumulated between 21 Jun and 14 Sep across seven task types, and nothing in the codebase deleted, swept or aged them: the table had exactly three writers, all in ai.service.ts. The newest of the eighteen was made by this audit, which disconnected Prisma while a register check was still in flight — the defect producing its own most recent instance while being investigated.

The threshold was measured, not picked. The slowest call this ledger has ever completed took 591s (p99.9 526s, p99 242s), and the longest timeout in the code is the register check's 900,000ms ceiling. One hour is 6.1× the slowest completed call and clears that ceiling, so it cannot reap a call that is genuinely still running. All eighteen orphans were already older than an hour: the two populations do not overlap, which is what makes a flat threshold safe here.

A new status is only honest if every reader learns the word, and there were three. The API's ledger view now maps through a shared runResult(). The other two readers are React components, each carrying its own copy of the same ternary, whose implicit else paints anything unrecognised green — the success colour. Left alone, the sweep would have turned eighteen stuck amber rows into eighteen green ones reading ABANDONED: strictly worse than the bug. A shared mapper does not cross the API boundary; a vocabulary change has as many readers as there are copies of the branch, and the type system counts none of them.

What the evidence is, and what it is not. The before and after come from one instrument — the same census query, run either side. The sweep's own returned count was deliberately not the evidence. Two caveats belong on the face of this: the elapsed time between boot and sweep is unrecorded, and attribution to that particular boot rests on the server pid changing from 81065 to 97243, not on a timestamp. The transition is attributable to the sweep by construction, since ABANDONED is written in exactly one place in the codebase.

The divergence from the reaper this codebase already had

stage-jobs.util.ts solved the same class of problem for stage jobs, and the new sweep diverges from it twice. Neither divergence was argued at the time — both were arrived at from AiRun's own measurements and only named afterwards, which is why they are written down here rather than left to read as taste.

Flat threshold against a scaled one. abandonAfterMs() takes ten times a job's own ETA with a 30-minute floor, because a stage job carries an estimateSec and its runtimes span orders of magnitude. An AiRun row carries no per-row ETA, and its measured population separates cleanly — every orphan older than an hour, every completed call under ten minutes. Scaling would add a parameter to a distribution that does not need one.

A new status against ERROR. The stage-job reaper marks abandoned jobs ERROR, deliberately: “a silent lock becomes a visible failure, which is the whole point.” That reasoning does not transfer, and the reason is the stronger half of the argument. AiRun's ERROR bucket is attempt-inflated — provider failover writes one row per attempt, so 1,685 ERROR rows are not 1,685 failed operations, and anyone reading a failure rate off that column is reading an attempt count. Folding "we never found out" into a bucket that is already ambiguous would make a second unrecoverable distinction. A stage job has no failover and no such inflation, so ERROR stays honest there.

Worth recording that the codebase already had the word and no status for it: StageJobVerdict is '' | 'expired' | 'abandoned', and the comment at scripton.service.ts:1058 reads “AN ABANDONED JOB IS MARKED ERROR, NOT DELETED”. A vocabulary that exists in comments and verdicts but not in the stored value is a distinction the data cannot carry.

How the bundling was caught

The commit was first made by staging whole paths. One of them, ScriptOnSettings.tsx, was already carrying 101 insertions and 5 deletions of someone else's uncommitted work — a new panel import, an API import, a navigation block — and git add <path> swept all of it in silently. Nothing in the command's output says that a file had other changes in it.

What caught it was arithmetic, not review: the diffstat read +111 for a change that was four lines. The fix was to reset, split the file's diff into hunks, and re-stage only the two that belonged to the commit; the other party's 108 lines were still uncommitted afterwards, and the file count was unchanged at 19.

Read the diffstat against your own change size before every commit: a number larger than what you wrote is the only signal that a shared path brought someone else's work with it.
