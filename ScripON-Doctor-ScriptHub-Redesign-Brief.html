Script Hub Redesign & Feature-Integration Brief

ScripON Doctor — the script intelligence layer, integrated.

Nine phases turning the full research programme into a premium, professional Script Hub: every engine — coverage, diagnostics, version-compare, the 17 re-creation transforms, rating & culture, markets, adaptation & development studios, greenlight, cost & audience — mapped to screens, components, data, APIs and a centralised AI layer, with an architecture recommendation grounded in an audit.

Foundation: the ScripON Doctor research spec (29 capabilities, 17 transforms) + the release-readiness audit. Decision asked of me: choose Option A vs B and justify. Name: “ScripON Doctor” (working title, easily changed). Date: 17 June 2026.

PHASE 1

Product & workflow analysis

Today's Script Hub is already the platform's single source of truth: a script tree with revisions and colour-revisions, tag-once breakdown, projection of scenes → schedule strips, sides/lining/annotations, an audio sub-module, and the TVC brief→script bridge. It is strong on centralisation and weak on intelligence, consistency and reliability.

How Script Hub touches every module

Bottlenecks

  • Fragmented AI (10 direct call sites, hardcoded model) → inconsistent behaviour, the live scaffold 500, no governance.
  • Dual paths: Movie-Magic import vs projection-sync vs legacy schedule-import can diverge.
  • Soft script↔strip link (hard-FK refactor declined) → integrity leans on projection logic.
  • Version drift: schema runs ahead of the live DB (db push, no migrations).
  • IA naming collisions across the platform (script vs master-script; locations-library vs production/locations).

Duplicate functionality

  • Two+ breakdown entry points historically; multiple budget generators (now merged).
  • Brief→script (TVC) and a future Develop/Adapt seed→script overlap — must share one engine.
  • Coverage exists ad hoc; will collide with the new data-grounded generator unless unified.

Missing industry-standard features

  • Data-grounded coverage in the house format; diagnostics; version-compare; rating/culture/relocation; adaptation & development studios; markets/greenlight; cost-optimisation; audience perspective; GLP — none exist today.

Poor UX patterns

  • No single 'Doctor' surface — AI actions scattered across panels.
  • Surface complexity: many panels, thin onboarding/empty states.
  • Sparkle/wand AI-hint icons were added then removed — pattern churn signals inconsistency.

PHASE 2

Information-architecture review — the recommendation
CriterionOption A · integrate into existingOption B · restructure

Ease of useFamiliar but crowded.Cleaner once learned; guided by a context Doctor panel.

Recommendation: Option B architecture, shipped the Option A way

Restructure the IA (Option B is clearly stronger on every criterion that matters at scale), but deliver it as a parallel, feature-flagged workspace that reads the same SSOT and runs beside the current Script Hub until cutover. This gives the better architecture without breaking anything — honouring the project's standing “don't break a thing” rule. It is not a rewrite of data; it's a new front door to the same script tree.

Proposed top-level IA: a script workspace with a small, fast left rail — Library · Write · Doctor · Create (Develop/Adapt) · Insights (Coverage/Diagnostics/Arc) · Production (Breakdown/Schedule/Budget) · Greenlight (Market/Audience/Cost/GLP) · Settings — and an omnipresent context-aware Doctor panel that acts on the open script or selected scene(s). Select → run any transform → compare variants → branch. Fewest clicks; AI is one panel away everywhere.

APIs

  • CRUD for each new entity (scripts, coverage, variants, diagnostics, profiles, forecasts, scorecards).
  • Search & filter across scripts/scenes/coverage/variants.
  • Bulk actions (approve variants, apply cost opportunities, export reports).
  • AI action endpoints routed through AiService (diagnose, transform, coverage, adapt, develop, rate, forecast, optimise) — async with progress.
  • Webhooks/notifications on run completion, approvals, greenlight decisions.

Business logic

  • Automations: rewrite → re-project to strips → re-cost (EFC) → regenerate coverage.
  • Dependencies: variants branch from a revision; coverage binds to a revision; never auto-commit.
  • Triggers: new colour revision → auto version-compare; brief/seed approved → scaffold.
  • Notifications: AI run done, low-confidence flagged, gate passed, decision memo ready.
  • Governance: every AI write carries provenance + confidence + PENDING→APPROVED lifecycle.
The keystone is the unified AiService + governance spine the release audit demanded: one gateway (model config, retries, streaming, token accounting), and every AI write carries prompt+model version, confidence, lineage and a PENDING→APPROVED lifecycle in AiRun. ScripON Doctor is its first and largest client — replacing the ten scattered call sites.
