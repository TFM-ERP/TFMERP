69 — Nothing guards the order of the ladder

A build cannot say that its SCENES predates its own BEATS

On the night of 14 Sep two operators generated on the same build at the same time, and the build records nothing about it. The order below is known only because both clocks were held by the people who ran them; the rows themselves are indistinguishable from an orderly ladder.

§21's guard is per-stage: startStage refuses a second concurrent run of the same stage. Two different stages carry no such relationship. SCENES was generated against a build whose BEATS did not yet exist, BEATS arrived twenty-eight seconds later, and the finished build now presents a complete, plausible ladder in which one rung was written before the rung it is supposed to be built on.

The stage version rows carry createdAt, so the order is recoverable by anyone who thinks to ask. Nothing asks. A ladder that records when each rung was written but never that a rung preceded its own foundation cannot tell a reader which results are built on what.

This also contaminates results taken from such a build without anyone noticing: the SCENES register score in §67's scope note came from exactly this state, and the only reason it is marked uncontrolled is that the collision happened to be observed.

70 — Two checks whose trigger may not occur in this material

A check that never fires on real output is a measurement about the check, not a pending result

Two instruments have now been exercised often enough that their silence is itself the finding.

The era check's comparison. Nine stage bodies across three builds have carried temporal language and not one absolute year. Every expression resolved is a relative distance — “seven years earlier”, “eight years ago”, “two days later”. The comparison the check exists to make needs a stage that dates itself: an absolute year and a relative distance in one sentence. The FAITHFUL direction asks, in as many words, for a dated flashback in Sequence Four; forty scene cards delivered it as “seven years after”. This is not a check waiting for its first chance. It is a check whose trigger this material does not appear to produce, and the honest reading is that its findings path is exercised by the replay and by §57's V2.6 contradiction, and nowhere else.

The truncation boundary. The predicates disagree only between 90% of the ceiling and a non-max_tokens stop. Two live SCENES runs landed at 82.8% and 62.0%, both end_turn, both making zero continuation calls — outcomes on which the old predicate and the new one agree. If SCENES routinely lands in the 60–85% band, the disagreement zone is not reachable in production, and the five-branch replay is the only evidence 0201a23 will ever have.

Record an unreachable trigger as a property of the instrument, not as work still pending; a check nobody can fire is not a check awaiting a run.

71 — The character bible writes to a row twenty-five builds share

A build's own cache is written correctly, and the shared workspace row is overwritten beside it

generateCharacterBible stores its result twice: :5259 upserts intakeProfile.characterBible — the one-row-per-project workspace record that every build in the ScripON Library reads — and :5260 writes the same array to the build. Reading prefers the build's own copy (:5209), so generation today is not affected by what the shared row holds. That is the only reason this is quiet rather than visible.

The trigger is narrower than “every SCENES run”, and worth stating precisely: the bible is generated only when the build has no cached copy and scenes exist. Every new build therefore clobbers the shared row once, on its first qualifying run, last writer wins. With 25+ builds against the one workspace project, the workspace copy describes whichever build most recently had none.

Both writes are swallowed. The upsert sits in try { … } catch { /* */ } and the build update carries .catch(() => {}) inside a second try — so a failed write to either place is indistinguishable from a successful one, and nothing on the build says which copy it is reading or whether the other exists.

This is §40's intake.treatment collision in a second field. A shared-by-default row plus a per-build cache is not a migration; until the shared write is removed it is two sources of truth, one of which is silently wrong for every build but the last.
