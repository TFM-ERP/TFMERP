Build blueprint · v1 draft

A field-ops & communication platform
for drivers, crews, dispatch & admins

We're turning the read-only driver web page into an installable, offline-capable field app, and adding a company-wide messaging backbone — text, voice notes, push-to-talk, locations, and media — all self-hosted, all free of paid subscriptions, with a tamper-proof audit trail visible only to admins.

Installable PWA Works offline One comms backbone, two surfaces Push-to-talk Immutable audit No paid SaaS AI-assisted

For the field

Drivers & crews get a one-handed app: today's jobs, live route, capture, and chat — usable with no signal.

For coordination

Dispatch, planners and supervisors talk to the right people through channels scoped to projects, units, jobs and trips.

For the record

Every message and file is retained immutably. "Delete" only hides; admins always hold the full history.

Settled before we build

The product · coordination

Comms backbone — one engine, two surfaces

We build one messaging service, not a chat per module. It appears two ways: a global inbox (the standalone app — every conversation in one place) and embedded threads (the same conversation shown inside the project, job or trip it belongs to). Same data, two doorways.

Global inbox

Slack/WhatsApp-style: all your channels, DMs, PTT rooms and broadcasts in one list. Where admins and dispatch live.

In-module threads

The Job #412 thread shows on the job page; the project channel shows on the project page. Context never lost.

Channels are scoped to things the system already knows

Nobody hand-manages groups. A channel is keyed to an entity, and membership is derived automatically from who's assigned to it. Cast a crew member to a unit → they're in that unit's channel. Assign a driver to a trip → they're in that trip thread with dispatch. Close the job → the channel auto-archives (and is retained).

Company Business unit (Production / Rental / Finance) Project Production unit Team / department Rental job Trip / leg Direct message Broadcast / announcement Live PTT room

"I'm stuck here" or "here's the gate".

Files & links

Documents, call sheets, external links.

Entity cards

Share a job, asset, inspection or invoice as a deep-link card.

Push notifications

Web Push (VAPID) — new job, message, approval.

Translation (later)

Multi-language crews chat across languages.

The product · live voice

Walkie-talkie (push-to-talk)

A channel can be a live voice room: hold to talk, release to listen, audio streams to everyone tuned in — exactly how a film set's radios or a fleet's dispatch work. Same membership model as text channels, so "Unit B set radio" or "Drivers on shift" becomes a live room automatically. Built on WebRTC (peer-to-peer for small groups, a self-hosted media server for bigger ones) — no subscription, runs on your server.

Hold to talk

One big button. Live audio to the room. Release to listen.

Async fallback

Off-room or offline? It becomes a voice note that delivers on reconnect.

Still audited

PTT sessions are logged; recordings retained per policy in the vault.

Needs signal. Live PTT is the one feature that can't run fully offline — but voice notes queue and deliver the instant the driver reconnects, so the channel still works in a dead zone, just asynchronously.
The product · dispatch & supervisors

The desktop side — command centre

Everything the field produces surfaces for the people coordinating it, in the existing Live Logistics command centre and the global inbox. This is where planners assign, dispatch talks, and supervisors watch.

Live map & roster

Real-time positions of on-shift drivers and units (from the continuous GPS stream), per-location status, crew counts, alerts.

Inbox & channels

All job/project/unit threads, DMs, PTT rooms and broadcasts. Send a pin, a gate code, a call sheet to exactly the right people.

Approvals & exceptions

Fuel/expense approvals, incident triage, the maintenance + substitution flow when a driver reports an unfit asset.

Broadcast

One-to-many announcements to a unit, a project, or the whole fleet — with read tracking.

The record · admin-only

Audit vault

Every message and file is written append-only. A user "delete" inserts a tombstone — the thread shows "message deleted", but the original content, the file copy, and who deleted it and when are retained permanently. Edits keep prior versions. Each item carries a content hash so you can prove it wasn't altered.

Visibility is admin-only. Drivers, crew, supervisors and dispatch never see the vault or deleted content. Only the admin role can open it — and every admin read is itself logged, so there's a record of who looked at what.

How it works

Offline-first

A service worker caches the app shell so it opens instantly with no signal. Two on-device stores (IndexedDB) do the rest: a read cache so the driver always sees today's work, and an outbox that queues everything they do until signal returns.

ON DEVICE
Read cache
Jobs, route, map tiles, chat history — readable instantly, offline.
ON DEVICE
Outbox queue
Photos, inspections, messages, GPS — saved & stamped with real time + location.
WATCHER
Service worker
Detects reconnect, flushes outbox in order, pulls fresh data down.
SERVER
Source of truth
Resolves order & conflicts, pushes updates to everyone.

Captured-at, not synced-at

Records reflect when the action truly happened in the field, even if it uploads hours later.

Conflict handling

Field is authoritative for field events; the server reconciles rare clashes and flags anything that changed under the driver.

Honest limits

Live navigation re-route & live PTT need signal; cached tiles still show the route and voice notes queue.

How it works

Storage & media pipeline

Server disk for now, foldered cleanly so it lifts to self-hosted object storage (MinIO) later with no app changes. Live files and their immutable audit copies live in separate trees, so cleaning the live store can never touch the vault.

/storage /chat/<scope>/<channel-id>/<year>/<month>/ → live attachments (downsized) /audit/chat/<channel-id>/<year>/<month>/ → immutable originals (write-once) /inspections /incidents /fuel /signatures → module evidence

Media is small on the wire, clear on screen

MediaShared copyKept in audit
Photos~1920px long edge, JPEG/WebP, ~200–500 KBFull-resolution original
VideoH.264/265 MP4, 720–1080p, ~1.5–2.5 Mbps, ~10–20 MBHigher-fidelity original
Voice noteOpus, a few KB/sec + transcriptOriginal audio

Transcoding uses FFmpeg (free, self-hosted, same Docker pattern as your TTS). Hard caps on size, type and duration are enforced at upload, so storage can't be bloated and unwanted file types are rejected. Thumbnails make lists load fast.

How it works

AI in the loop

Optional, low-cost, and graceful offline (queue and process on sync). Nothing here adds a recurring bill.

Voice → record

Transcribe a driver's voice note into a written incident or inspection note (local Whisper).

Thread summary

"What changed, what's blocked, who's waiting" over a long job/project thread (existing Anthropic key).

Smart routing

Read an unclear "I'm stuck here" and route it to the right supervisor with context.

How it works

Data model (new tables)

Additive to your Prisma schema — nothing existing is disturbed. Channels use a polymorphic scopeType + scopeId so any entity can own one.

Channel

id · scopeType (PROJECT|UNIT|JOB|TRIP|TEAM|DM|BROADCAST|PTT) · scopeId · title · isPTT · archivedAt

ChannelMember

channelId · userId/driverId · role · joinedAt · derived-from-assignment flag · lastReadAt

Message

id · channelId · authorId · body · type · replyToId · createdAt · gps · contentHash · deletedAt · deletedBy

MessageVersion

messageId · version · body · editedAt — prior versions retained for the edit trail

Attachment

messageId · kind · sharedPath · sharedBytes · originalPath · originalBytes · transcript · contentHash

AuditAccessLog

adminId · target (message/attachment id) · action · at — every vault read recorded

PttSession

channelId · startedAt · participants[] · recordingPath (per policy)

OutboxItem (device)

local only · kind · payload · capturedAt · gps · syncState — flushed on reconnect

Flows & plan

Phased roadmap

Build in slices that each ship value. The PWA shell comes first because everything else rides on it; PTT and native come once the text/comms backbone is proven.

Now
  • PWA shell: installable, offline cache + outbox, Web Push
  • Redesigned map-led Today screen + bottom nav
  • Continuous on-shift GPS to the command-centre map
  • Capture upgrades: stamped camera, voice notes, QR scan, signature
Next
  • Comms backbone: channels, scoped auto-membership, two surfaces
  • Text, photo/video (transcoded), location pins, entity cards
  • Immutable audit + admin-only vault + access logging
  • MinIO storage move; Whisper transcription; thread summaries
Later
  • Push-to-talk live voice rooms (WebRTC → mediasoup)
  • Client-facing booking channels & real-time translation
  • Native app (React Native / Expo) reusing the same APIs
  • Background location & richer offline maps
Before any of this: the pending migration (TowCoupling + mileage + substitution fields) still needs running, and the driver-portal coupling/route work is uncommitted. We close those out, then start the Now column.
