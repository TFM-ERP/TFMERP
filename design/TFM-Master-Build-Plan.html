How we ship the revamp without breaking what works.

This is the single source of truth that turns the findings into shipped work — design and code and database and the small new options. Every step is additive, flagged, and reversible, so the live system keeps running the whole way.

Companion to the UX/UI Revamp Findings. Stack: NestJS + Prisma/Postgres · Next.js 14 App Router · Figma (Graphite & Gold). Governing rule: don’t mess a thing.

AWhat’s approved (scope lock)

Everything in the findings report, plus the functional layer — captured so nothing gets lost:

  • One Workspace shell (Rail · Toolbar · Canvas · Panel) every module inherits; content-first, collapsible chrome, full-screen/focus.
  • Dual token system — Graphite & Gold (night) ↔ Studio Light (day) + Ink & Paper reading mode + AAA contrast + density.
  • IA regroup into lifecycle clusters (Develop / Prep / Shoot / People / Money / Admin) with “bring parts together” consolidations.
  • The loved boards are canonical: Script Reader, Daily Call Sheet (+ Notes & Weather), Transport Dispatch.
  • New features (not graphic-only): theme governance (user pref + admin policy), ⌘K command palette, saved views, cross-module deep-links, notifications feed, full-app PWA, RTL/Arabic.

BThe “don’t mess a thing” protocol

Non-negotiable rules for every change in this plan:

✓ Seven safety rules
  1. Additive only. Add new files, columns and tables. Never delete or rename anything live until its replacement is proven and switched on.
  2. Parallel, not replace. The new shell/nav is built alongside the current UI; the old layout stays the default until a page is migrated and verified.
  3. Feature-flagged. New shell, new nav and each feature ship behind NEXT_PUBLIC_FF_* flags — off in production until you flip them.
  4. Non-destructive DB. Only additive Prisma models/columns with defaults. No drops, no renames. Back up before any db:push.
  5. Verify gates. Each step must pass tsc --noEmit = 0, next build, prisma validate, and a smoke check before the next step starts.
  6. One module at a time. Migrate Script, verify, then the next — never a big-bang switch.
  7. Reversible. Each phase is its own branch/PR; rollback = flip the flag or revert the PR. Nothing is one-way.
⚠ what we will NOT do
No destructive migrations, no mass find-and-replace across pages, no removing a working module before its replacement passes verification, no touching auth/permissions or financial logic as part of a visual change.

frontend/src/styles/tokens.css — semantic tokens + the six themes + [data-mode] / [data-read="ink"] / [data-contrast="aaa"] / [data-density]. Imported once in the root layout. Existing styles stay; pages opt in by reading var(--…).

0.3 · Theme runtime

  • Backend: a small preferences module — GET/PUT /me/preferences, GET/PUT /org/theme-policy (admin-guarded).
  • Frontend: lib/theme.tsx — ThemeProvider resolves policy ∩ preference (forced → org; restricted → pref ∩ allowed; open → pref) and sets the data-* attributes. Settings → Appearance and Admin → Theme policy pages (the demo, wired to the API).

DVerify & rollback

Every step runs the same gate:

› verify gate
frontend: npx tsc --noEmit # must be 0 errors frontend: npm run build # must pass backend: npx prisma validate # schema ok backend: npm run build # must pass manual: smoke the touched screen + one unrelated screen

Rollback: each phase is a branch/PR. To undo — flip the NEXT_PUBLIC_FF_* flag off (instant, no deploy) or revert the PR. DB additions are harmless if unused; they can stay or be dropped in a later reviewed migration. Nothing in this plan is one-way.
