TFM-System · Architecture Proposal

One Script to Feed Them All

Centralizing script upload, color-revision versioning, AI breakdown, and downstream sync into a single source of truth that projects into scheduling, casting, locations, budgeting and call sheets — with production-standard revision tracking and far fewer steps.

1 The real problem: three scripts, not one

An audit of the codebase shows the chaos isn't just duplicate buttons — the same screenplay is represented in three systems that never reconcile.

System A

Stripboard / Breakdown

production/breakdown + scheduling. Upload → parse → AI element tagging → ProductionStrip + BreakdownElement. The only path that runs AI and the only one feeding budget, DOOD, cast and call sheets.

System B

Script Hub / Documents

production/script. Upload → parse scenes → ScriptDocument / Revision / Scene. Holds the real PDF, revisions, annotations, lining, sides — but produces no breakdown elements (a $0 local heuristic only).

System C

Script Library

MasterScript — a company-level script linkable into many projects, copied in as a System-B document. Scenes stored as denormalized JSON.

Headline finding. The proper, revision-tracked script (System B) is breakdown-blind; the AI only ever runs on a separate strip-side upload (System A). A user can upload the same screenplay twice and get two unrelated representations that never sync. There are two different parsers and two scene schemas for the same file.

2 What the industry does

Modern production platforms (StudioBinder, Filmustage, Scenechronize/Movie Magic) converge on one model: the script is the master; you tag once; everything else is a projection that re-syncs on a new revision.

Single-source sync

  • StudioBinder: "Syncing your script ensures screenplay updates are applied across your entire project — breakdowns, stripboards, shot lists, call sheets stay on the latest version."
  • Filmustage: structured breakdown "keeps everything in sync when the script changes — updating breakdowns and reports instead of forcing teams to restart." Every tagged element "becomes a budget line item." AI "links all mentions" of an element across the script.
  • Tag an element once; it flows to schedule, budget, cast and reports. A new draft → a diff/sync, never a re-do.

Production-standard revisions

The WGA colour wheel, in order:

White Blue Pink Yellow Green Goldenrod Buff Salmon Cherry Tan

…then Double White, Double Blue… if it keeps going. Paired with locked pages (freeze page numbering for production), A-pages (3 → 3A when content expands), and asterisk revision marks on changed lines. "Lock the script" is the gate that starts scheduling.

The principle to adopt: the screenplay is not an input to five tools — it is the spine. Each module renders a view of the current locked revision, and re-renders when a new revision is approved.

3 Proposed architecture — "Script is the Spine"

Collapse the three systems into one. The Script Hub document + its active locked revision becomes the single source of truth. Breakdown is tagged on the script's scenes. Everything downstream is a generated projection.

All five read the same tagged master. None of them ingest or re-parse a file.

① One front door

The only place a file is uploaded/parsed is the Script Hub revision uploader (System B's pipeline, which already does PDF + revisions + annotations). The second parser is retired. Every other "import" becomes a shortcut that opens the hub or triggers the shared pipeline — never a parallel ingest.

② Tag once

The AI breakdown engine is re-pointed to run over a revision's ScriptScene rows, writing BreakdownElement bound to sceneId (the master) — not to a strip. It runs once per revision, with a per-scene brokenDownAt stamp and a source flag so manual edits are never wiped.

③ Project, don't duplicate

Strips, budget lines, casting calls, per-diem and call-sheet inputs are generated views of the tagged scenes, linked by id. One "Sync from script" action refreshes them; a new revision produces a reviewed change-list, not a silent overwrite.

4 Data model — additive deltas only

Every change is additive and nullable, so existing rows and queries keep working (the project's governing rule: "don't mess a thing"). No destructive migration.

5 Change propagation — the reviewed "sync", not a silent overwrite

When a new revision is locked, the system computes a diff and shows a change-list the AD/producer approves. Locked or hand-edited downstream items are protected — they warn, they don't get clobbered.

Example change-list

  • ~ Scene 7 pages 2.0 → 3.25, +2 background → update strip + budget qty
  • － Scene 22 deleted → its strip is locked on Day 4 ⚠ confirm removal
  • ↻ Scene 3 moved INT→EXT → re-flag for sun/daylight conflict check

Protections (the "don't mess a thing" gate)

  • Locked strips / published call sheets → warn before change, never auto-rewrite.
  • Manually-tagged elements (source=MANUAL) → preserved across re-sync.
  • Budget lines the user edited → flagged, not overwritten.
  • Every apply is written to ScriptSyncLog and is reversible.

7 The unified experience

One Script workspace (the hub)

  • Revisions — colour wheel, lock the script, A-pages, revision marks, diff vs prior
  • Breakdown — tag once (AI-assist + manual), element library, per-category
  • Scenes — the parsed spine (the unit everything derives from)
  • Projections — live "in sync / drift" badges for Schedule · Budget · Casting · Locations · Call sheets, with one Sync button + change-list
  • Annotations · Lining · Sides — existing, unchanged

Everywhere else

Modules drop their own upload/import buttons and instead show a small status chip:

Script vPink · locked · in sync
⚠ 3 scenes drifted — Sync

One mental model: "this view comes from the script." No more wondering which upload is the real one.

8 Phased, additive migration

Nothing is ripped out up front. Each phase ships value and is reversible; the old paths keep working until the new one is proven.

P0
Bridge (no breakage). Add the additive fields (BreakdownElement.sceneId, revision colour/lock, ScriptSyncLog). Make the M6 reconciler the canonical scene↔strip link by id. Ship a read-only Projections status panel in the Script hub showing drift. Nothing removed.
P1
Unify ingest + tag-once. Re-point the AI engine to run on a revision's scenes (elements on sceneId), with brokenDownAt + source idempotency. Route Schedule "Import/Full-setup" and Project-creation to call this shared pipeline. Old buttons become shortcuts.
P2
Projection engine + change-list. "Sync from script" orchestrator generates strips/budget/cast/per-diem/call-sheet from the master; new revisions produce the reviewed diff change-list with locked-item protection. Collapse the 3 budget generators to 1.
P3
Revision standard + UX polish. Colour-wheel automation, locked pages / A-pages / revision marks, the unified Script workspace tabs, retire the second parser, demote duplicate buttons to status chips.

9 Decisions for you

A few genuine forks shape the build. My recommendation is marked; tell me where you'd steer differently.

A · Where does the hub live?
Promote the existing Script module to the single source of truth (recommended — it already owns PDF, revisions & annotations), vs. build a new top-level workspace.
B · Propagation model.
New-revision changes flow via a reviewed change-list the producer approves (recommended — safe, industry-standard), vs. fully automatic propagation.
C · Duplicate entry points.
Keep contextual shortcuts (Schedule, Casting) that deep-link into the one engine (recommended — discoverability without duplication), vs. hard-remove them so the Script hub is the only door.
D · The strip ↔ scene relationship.
One scene → one strip, auto-generated & linked by id (recommended), vs. let strips be split/merged independently of scenes (more flexible, looser sync).
Net effect. One upload. One AI pass per revision. One tagged master. Five modules that render it and stay in sync through a reviewed change-list — with real colour-revision tracking underneath. Fewer steps, no divergence, production-grade.
