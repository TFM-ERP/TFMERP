Final research result · senior UX / IA / design-system review

From a pile of modules to one adaptive workspace.

You don’t need 200 prettier screens. You need one operating model applied everywhere: content first, chrome that collapses to icons and expands on demand, related parts brought together, and a single token system that flips between night (Graphite & Gold) and day (Studio Light) — with the Script Reader as the proven template.

Scope: full platform (desktop + tablet + mobile). Inputs: the six-direction explorer, the Script Reader study, your stated preferences (clustering / relocation / Ink & Paper / full-screen reader), 2026 SaaS & production-tooling research, and your existing NestJS + Next.js + Figma (Graphite & Gold) system.

0The verdict

The platform’s problem isn’t visual taste — your Graphite & Gold direction is strong. The problem is structural inconsistency: ~20 modules that each grew their own header, toolbar, table and spacing; a long flat sidebar that hides depth; and content-heavy screens (Script, Scheduling, Casting) where persistent chrome eats the canvas. The fix is to stop designing pages and start designing one shell that every module plugs into.

This is exactly what you reacted to in the explorer: a single screen where parts are clustered, relocated and brought together, and what you love in the reader — full-screen focus with a toolbar that collapses to icons (☰ 🔎 A− A+ ⤢) and the Reader / Pages / Audio segmented control. We make that the law of the system, not a one-off.

1What the research says

The 2026 consensus across enterprise SaaS and production tooling points in one direction, and it backs your instinct:

  • Density is out; intelligent density is in. The era of cramming every chart above the fold is over — surface “is everything OK?” first, then let people drill in. Progressive disclosure is the strongest pattern of the year.
  • Content-first, context-aware layouts. Leading tools adapt the workspace to the user’s role and task instead of showing every control at once. The primary artifact (a script, a board, a sheet) should own the canvas.
  • Semantic design tokens, swapped by mode. Light↔dark is a token-set swap, not a redesign — color.surface.1, not a hex. This is how Linear, Stripe, Mercury, Vercel and Notion stay consistent at scale.
  • Production tools win on flow, not features. StudioBinder’s edge is auto-populated call sheets and in-context actions — fewer hops between modules. Screenplay tools (Final Draft, Arc Studio, WriterDuet) converge on one thing: a distraction-free, industry-standard script surface in Courier Prime.
✓ What you already got right — keep it
Graphite & Gold as the brand identity; the Ink & Paper reading mode; the component seeds in Figma (Button/Chip/Badge/Card/List Row/Tab Bar); the project-scoped Transport Captain console; the mobile /m app. These become the foundation, not throwaways.

2Audit findings — what’s actually wrong now

Honest, specific, and fixable. Eight findings, ranked by impact:

⚠ F1 · Navigation sprawl
~20 modules sit in one flat sidebar with no grouping by workflow. New users can’t find features; power users scroll. No sense of “where am I in the production lifecycle.”
⚠ F2 · No shared shell
Each module page invented its own header, toolbar and table over time. Spacing, type sizes, radii and button styles drift page-to-page — the system reads as several apps stitched together.
⚠ F3 · Chrome competes with content
On Script, Stripboard, Casting and Locations the persistent sidebar + page header consume 25–35% of the canvas. There’s no focus / full-screen mode for the work that needs it most.
⚠ F4 · Density without hierarchy
Dashboards and tables show everything at once instead of leading with the one answer that matters, then drilling in. High cognitive load, slow scanning.
⚠ F5 · Component drift vs. the design system
Buttons, badges and cards are styled ad-hoc per page rather than from the Graphite & Gold library; tokens exist in globals.css but usage is inconsistent, so a restyle means editing dozens of files.
⚠ F6 · Responsive = shrink, not adapt
Desktop tables and panels merely shrink on tablet/phone; the new /m app is a separate build rather than the same shell adapting. Two code paths, two maintenance costs.
⚠ F7 · Script surfaces are fragmented
Reader, Pages and Audio Studio look and behave differently. The “real script” experience you keep asking for isn’t unified — the thing users touch most is the least consistent.
⚠ F8 · Mode & access aren’t systematic
No clean light/dark token swap; night-mode/AAA readability isn’t first-class for on-set use; and (MENA deployment) there’s no RTL/Arabic story yet — a hard release blocker for your market.

3The core move — one “Workspace” shell

Every heavy module stops being a bespoke page and becomes content inside one shell with four parts. This is the single highest-leverage change in the whole plan.

  • Rail — global navigation. Full labels on desktop; collapses to icons on smaller viewports or on demand; click an icon to expand contextual actions + labels.
  • Toolbar — contextual per module. For the Script that’s Reader / Pages / Audio + ☰ 🔎 A− A+ ⤢; for Scheduling it’s view-switch + auto-balance; for Finance it’s period + export. Same anatomy, different verbs.
  • Canvas — the primary artifact (script, stripboard, board, sheet) owns the space. Always the largest region.
  • Panel — a progressive-disclosure side drawer (breakdown, notes, details, comments) that opens when needed and gets out of the way otherwise.
Desktop · expanded
Tablet · rail → icons
Mobile · content + bottom nav

The same shell adapts across breakpoints instead of being rebuilt — the desktop rail becomes an icon strip on tablet and the bottom tab-bar on phone (reusing your /m patterns). One code path, three experiences.

✓ Your reader is the template
The Script Reader already proves this model: artifact-first canvas, segmented control, scene navigator (Panel), full-screen, A−/A+. We’re generalising what you already built and loved into the shell every module inherits.

“Bringing parts together” — concrete consolidations

These are the relocations you liked, made real (each reflects in code, not just design):

  • Script workspace = Reader + Pages + Audio Studio + Breakdown + Sides under one shell with the segmented toolbar — instead of four separate destinations.
  • Scheduling workspace = Stripboard + Calendar + DOOD as views of one board, not three pages.
  • Transport (Captain) = Dispatch + Map + Garage + Crew (already consolidated — use it as the proof pattern), embedded per-project.
  • Money workspace = Cost report + POs + Petty cash + Contract values share one ledger surface.
  • Casting → Comms hand-off kept and surfaced: confirming a role spins up the cast channel in-context (fewer hops, the StudioBinder lesson).
✓ locked — transport dispatch (loved)
The Captain dispatch board is the reference for a live-operations workspace: a left-to-right FSM kanban (Unassigned → Dispatched → En route → On board) with run cards carrying ETA / VIP / TRUCK chips, a live map with colour-coded vehicle pins and a “9 cars live” status, tabbed Dispatch / Map / Garage / Crew. This pattern (kanban + live map + status chips) is reused anywhere the system tracks moving things in real time.

5Design system & standardization

One token system, two modes, one reading mode. Everything visual references a semantic token so a restyle is a token edit, never a find-and-replace.

› token model (globals.css)
:root maps raw palette → semantic tokens. [data-mode="dark"] = Graphite & Gold, [data-mode="light"] = Studio Light. Reading surfaces add [data-read="ink"].

--surface-0/1/2/3 · --text-1/2/3 · --border-1/2 · --accent · --accent-on · --gold · --ok/warn/danger (+ soft) · --radius · --space-1..6 · --font-sans/serif/mono

Standardized scales

  • Spacing — 4px base (4/8/12/16/24/32). No more arbitrary 7px/13px paddings.
  • Type — one ramp: 11 / 12.5 / 14 / 16 / 18 / 23 / 32. Inter for UI, Fraunces for display, Courier Prime for script.
  • Radius — 8 (controls) / 12 (cards) / 999 (pills). One value per role.
  • Elevation — borders in dark, soft shadows in light; never both.

Component library (the canonical set)

Promote the Figma seeds into a complete, code-backed kit; retire ad-hoc variants:

  • Button (primary/secondary/ghost/danger), Chip, Badge/Status, Input/Select/Textarea, Toggle/Checkbox/Radio, Card, Metric/stat, Table (sortable, sticky, virtualized), Toolbar, Segmented control (the Reader/Pages/Audio pattern), Side Panel/Drawer, Modal, Toast/notification, Empty / Loading / Error states, Tab Bar (mobile).
→ change
Build these once in components/ui/*, bind to tokens, mirror 1:1 in the Figma Graphite & Gold library, and connect with Code Connect so design ↔ code stays honest.

6The Script north-star — “a real script,” everywhere it appears

This is the surface you care about most, so it sets the bar. The Script becomes one workspace with three views behind a single segmented control:

  • Reader — Ink & Paper by default: warm sheet, Courier Prime, industry-standard formatting (sluglines, action, character, dialogue, dual-dialogue, transitions, scene numbers, revision asterisks + colored revision pages). Full-screen / focus mode. A− / A+ sizing. Scene navigator and Breakdown ride in the Panel.
  • Pages — the same script as paginated, printable sides with revision marks and watermark-on-share.
  • Audio Studio — the same script, now a table-read / ScriptON surface: per-character audio, line-synced playback — but visually unmistakably the same script.
✓ exactly what you flagged
The Reader / Pages / Audio segmented control and the ☰ 🔎 A− A+ ⤢ toolbar you sent become the canonical “document workspace” chrome — reused by Contracts, Call Sheet preview, and any document surface. Reader Portal (talent-facing) inherits the same reading mode so what an actor sees matches what the AD sees.

7Responsive & adaptive — adapt, don’t shrink

The shell changes behaviour by device, not just scale:

  • Desktop (≥1200px) — full rail, multi-panel (Canvas + Panel side-by-side), dense tables, keyboard shortcuts, multi-monitor friendly (detachable reader/full-screen).
  • Tablet (768–1199) — rail collapses to icons; Panel becomes an overlay drawer; larger touch targets (44px); same productivity.
  • Phone (<768) — content-first single column; rail becomes the /m bottom tab-bar; Panel becomes a bottom sheet; primary action as a thumb-reachable button. Reuse the live /m app rather than a second design.

Browser- & context-aware

  • Respond to viewport (not device guesses), touch vs mouse (hover affordances vs tap), orientation (landscape reader), and offer a PWA / installable experience (already in place for /driver and /m — extend to the main app).
  • RTL / Arabic — first-class mirroring for your MENA market (logical CSS properties, mirrored rail/toolbar, Arabic UI font). Treat as a release gate, not a nice-to-have.

9What changes in code

The revamp is mostly consolidation, not rewrite. Six concrete moves:

  1. Tokenize frontend/src/app/globals.css — semantic tokens + [data-mode] / [data-read] swap. One source of truth for both themes.
  2. Build the shell — components/workspace/Workspace.tsx exposing Rail / Toolbar / Canvas / Panel slots + focus/full-screen + breakpoint behaviour.
  3. Regroup nav — refactor (dashboard)/layout.tsx from a flat list to lifecycle clusters with a collapsible icon rail (no route changes required day one — just grouping + the rail).
  4. Extract UI kit — components/ui/* (Button, Table, Toolbar, SegmentedControl, SidePanel, Empty/Loading/Error). Replace per-page styles module by module.
  5. Reading mode — a ScriptSurface component shared by Reader / Pages / Audio / Reader Portal so the script always reads identically.
  6. Adaptive + RTL — drive layout off viewport + input type; add dir="rtl" support via logical CSS properties; fold /m in as the phone breakpoint.
→ sequencing that protects you
Ship the shell + tokens behind the existing routes first (invisible to users), migrate one module (Script) as the proof, then roll the rest module-by-module. No big-bang rewrite, no frozen release.

New features this unlocks — not graphic-only

The revamp surfaces real, reasoned capabilities that talk to the system and cut work — each tied to a finding, not decoration:

  • Appearance & theme governance (F8) — users set their own look; admins set policy: open, restricted to a curated set, or forced org-wide, plus a default for new users. Why: brand control for client/investor-facing studios without killing personalisation.
  • Command palette (Ctrl/⌘K) (F1) — jump to any module, project or record in two keystrokes. Why: kills the flat-sidebar hunt.
  • Saved views & filters (F4) — per-user saved table sorts/filters, shareable with the unit. Why: people re-run the same queries every day.
  • Cross-module deep-links (F1/F7) — a scene links to its call sheet → dispatch run → cast channel. Why: the StudioBinder lesson — fewer hops, data in context.
  • Contextual notifications / activity feed — call sheet published, contract signed, run wrapped, weather hold. Why: the system tells you instead of you checking.
  • PWA for the whole app + RTL / Arabic (F6/F8) — installable, offline-tolerant, mirrored for MENA. Why: hard release-gates for your market.
› data model — theme governance (new)
UserPreference { themeId, density, readingMode, highContrast }
OrgThemePolicy { mode: open|restricted|forced, allowedThemeIds[], forcedThemeId, defaultThemeId }
Resolve on load: forced → org theme; restricted → user pick ∩ allowed; open → user pick. Apply via data-theme / data-contrast on the shell. (Live demo: ux-theme-governance.html.)

11Roadmap

  • Phase 0 — Foundation. Tokens + mode swap, the Workspace shell, the UI kit (code + Figma, Code-Connected). Invisible to users.
  • Phase 1 — Navigation & IA. Lifecycle clusters + collapsible icon rail. Immediate perceived-quality jump.
  • Phase 2 — Module migration. Script first (the north-star), then Scheduling, Casting, Locations, Finance, Contracts — each onto the shell, content-first.
  • Phase 3 — Adaptive, a11y, RTL, polish. Breakpoints, /m unification, AAA night mode, Arabic/RTL, empty/loading/error, QA & perf (virtualized tables).

Each phase ships independently — you’re always releasable, and the system gets visibly better at every step.
