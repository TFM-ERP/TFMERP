1 · Creative blend — expanded, and the "layer" generalised

Research model (StudioBinder/MasterClass/Wikipedia): a story has a base genre (the noun) and you can stack overlay layers (the spice) on top — "in romantic suspense, suspense is the base, romantic is the overlay." So the screen's "fantasy layer" becomes a general blend layer, with fantasy as one option.

Sacred-content guardrails — remove gods/prophets, keep folklore enforced

Grounded in the established film convention (Islamic aniconism; The Message 1976, Muhammad: The Last Prophet 2002, Bilal 2015 never depict the Prophet; Ben-Hur/Prince of Egypt never show Jesus' face / blend God's voice). The mythical-elements list drops "Gods"; folklore stays.

Tier 1 — hard (always on; the AI refuses + offers the compliant alternative):

  • Never depict, name, voice, or write dialogue for God / any deity, or for prophets (Muhammad, Jesus, Moses, Abraham…). Convey via narration, POV, off-screen, light/veil — the standard conventions.
  • No scripture verbatim passed off as character speech; reference/paraphrase with attribution, never alter sacred text.
  • No mockery, desecration, or sexualisation of the sacred (figures, scripture, rituals, sacred places).

Tier 2 — reverence (default, adjustable): revered family/companions handled with dignity (often off-screen or via a representative character); sacred places/objects depicted accurately. A "depiction-convention helper" appears when a sacred era is chosen.

Tier 3 — explicitly allowed (don't over-block): DjinnGhoulIfritMarid and mythical beasts (Qur'anically/folklore-affirmed, not objects of worship); all human/historical characters (caliphs, poets, soldiers); religion as theme/setting.

Enforcement: each era carries a sensitivityTier; Prophetic/early-Islamic auto-enable Tier-1. A prophet/deity name-list triggers redirect-not-refusal. Baked into the intake steer that runs on every stage; a human-review flag on borderline scenes before export.

6 · Source v2 — website + HTML files deep-think

Adapt gains two real source types beyond paste/upload: a website URL (e.g. "everything about this character is on this site") and HTML file upload. The backend fetches → extracts clean readable text → feeds the AI; optionally light-crawls a few internal pages.

Recommended stack (verified June 2026): @mozilla/readability+jsdom (or @extractus/article-extractor — takes a URL or HTML string, lighter) for extraction; Crawlee CheerioCrawler for the optional light crawl (maxRequestsPerCrawl, maxCrawlDepth, same-hostname, robots opt-in). avoid @postlight/parser & unfluff (abandoned, cheerio 0.22).

Security (must-do, per OWASP): SSRF guard — resolve all A/AAAA records, block private/reserved/metadata 169.254.169.254; maxRedirects:0 (redirects bypass the check); size + timeout caps on the decompressed stream; robots.txt is advisory (RFC 9309) so respect it + rate-limit; ToS/copyright are separate from access — only fetch what the user pasted, store source+timestamp for provenance. HTML upload runs the same extractor with zero network egress.

7 · Named, savable, navigable builds + stage reset deep-think

Today there's one implicit pipeline per project. Your ask: name a build, save it, switch between several Adapt/Develop builds, and reset a stage. New structure:

DevelopmentBuild (named)⊃IntakeProfile (the brief)+DevelopmentStages → versions
  • New build → asks for a name (e.g. "Antara — mythic cut") + opens the intake.
  • Build switcher (like the project pill): list + switch between builds on the same project; each remembers its intake + ladder.
  • Reset a stage → clears that stage's versions (and optionally everything downstream) so you can regenerate from a clean rung; the build + earlier stages stay.
  • Save is automatic (persisted) — builds survive reload and are listable.

Data model: new standalone DevelopmentBuild { id, name, status, createdAt } (no project at birth — see §8); add buildId to IntakeProfile + DevelopmentStage (so multiple builds can run unattached). Reset = delete a stage's StageVersions (+ optional cascade downstream). One db:push.

8 · Promotion — link a finished build into a project lifecycle

Builds are born unlinked. Development/adaptation is optionality — many cheap, disposable, resettable builds in flight; a project is a commitment that drags heavy machinery (budget · schedule · breakdown · crew · GL · call sheets). Attaching a project at logline/treatment stage spawns junk projects and pollutes financials, so a build carries no project until you decide it is ready — which is also what keeps the governance split clean (standalone develop = no approval workflow; project-level changes = approval).

The promote action deliberate, not automatic

Standalone build→Draft / Greenlit→Promote→Add to existing projectorStart new project→Script Library · master rev

Available at any rung but nudged at Draft+ (you usually promote a draft or a greenlit treatment, but the system will not hard-block an early greenlight). Two destinations:

  • Add to an existing project → the script lands in that project's Script Library as a master script; breakdown / schedule / budget then run off it.
  • Start a new project from it → spins up the project shell and seeds it with the script + metadata in one step.

What transfers at promotion

Carried into the projectStays on the build
The chosen locked StageVersion → the project's first master revision (e.g. WHITE draft); title · format/genre · logline; the intake creative brief (tone · setting · culture · comps · budget tier · intent); coverage if generated; a provenance back-link to the originating build.The full stage/version scratch history (loglines, alternate treatments, rejected drafts) — linked for lineage, not dumped into the clean project.

Snapshot, not live sync the one real decision — recommended

Promotion takes a frozen copy. After linking, further work happens as project revisions; if you keep developing the build, you can "push an updated draft" as an explicit action that re-promotes into the same project. Two-way live sync is deliberately rejected — it creates reconciliation conflicts (which side wins when both edit?). One-way snapshot keeps lineage clean and still lets you re-push.

Build status lifecycle: DraftReview / CoverageGreenlit / ReadyPromoted (Linked to project). A build links to at most one project (1:1); re-promoting updates that project rather than creating a second link.

Data model

DevelopmentBuild becomes truly standalone (no required projectId at birth) and gains status plus the link fields linkedProjectId? · linkedScriptId? · promotedVersionId? · promotedAt?. The existing promoteToScript service extends to (a) run from a standalone build, (b) optionally create the destination project, and (c) write the snapshot + provenance. No live binding back to the build after promotion.

9 · Data model & phased plan

Schema (one db:push): standalone DevelopmentBuild (nullable project link · status · linkedProjectId/linkedScriptId/promotedVersionId/promotedAt); buildId on IntakeProfile + DevelopmentStage; IntakeProfile += blendLayers Json, treatment, settingPlace/era/world Json, cultureEra, sensitivityTier, guardrails Json, projectIntent, budgetTier, sourceKind (paste|file|url|html). Backend: web-ingestion service (extract+crawl+SSRF), guardrail injected into the steer (Tier-1 hard rules + era tier), build CRUD + stage-reset + promote(existing|new project) with snapshot + provenance.
