72 — Twenty settings, none of them stored

The typed row rejected the whole save while the jsonb brief beside it took every value

An intake was saved at 07:57 with a 105,177-character paste and twenty auto-filled settings. The build it produced carries all of it. The intake_profiles row carries none of the saved fields: settingEra still "", sourceText still 0 characters, realBased and researchSubject still at their schema defaults, and not one of the twenty settings present. Before and after came from one instrument — the whole row, snapshotted before the save and diffed after.

The timestamp is not the evidence, and a first reading of this section said it was. An early diff showed 0 of 60 columns changed with updatedAt frozen at the previous night's 20:46:34.217Z — and that was simply a read taken too soon. Thirty-one seconds after the build was created, a different writer landed on the same row: the research-notes path rewrote researchNotes and moved updatedAt to 07:57:32.868Z. Two columns of sixty, neither belonging to the intake save. So the row was writable and reachable throughout; the save's own fields are absent on their own merits. On a row with more than one writer, a moved timestamp proves that something wrote and a frozen one proves only that you read before it did — neither identifies the writer.

This settles a mechanism that was read wrongly once already. The earlier reading was coercion — a number arriving in a Boolean column and being flattened to true. It is not coercion. It is rejection: nothing is written at all, and the two values that looked coerced were simply the schema defaults (realBased Boolean @default(false), researchSubject Boolean @default(true)) still sitting where they always were. Coercion and never-written are indistinguishable from the values alone. What separates them here is field-level absence measured against a snapshot of the same row — every saved field still at its pre-save value while the brief beside it holds all of them — and not the timestamp, which another writer moved.

Two stores of the same fields, one typed and one jsonb, do not fail together: the permissive one accepts what the strict one refuses, and the write that fails is the one nobody is reading.

The era value reaches the brief and never the column

The analysis extracted “Present day, with a prologue set seven years earlier” and the intake screen showed Era empty. Two dead ends were possible: a control that cannot represent the string, or storage that never receives it. It is neither of the expected ones — the string is in brief.settingEra verbatim, so the control represented it perfectly, and the column is empty because the whole row write failed.

Every recent build carries era prose in its brief; the shared column has been "" throughout. The era check reads its anchor from the brief, so it is not starved by this — but the screen a writer looks at shows blank for a value every build already has.

A number with two positions

realBased is declared { kind: 'number', min: 0, maxNum: 1 } and the recommender emitted 0.25. Every reader of it is a bare truthy test — :2312 if (i.realBased), :1591 i.realBased ? … : null, knowledge/index.ts:33 if (!brief.realBased) return ''. So the field has exactly two positions, 0 and not-0, and 0.25 produces a byte-identical prompt to 1.0. A value chosen to mean “mostly invented” is indistinguishable from documentary. researchSubject at 0.7 has the same shape.

The defect is not that the flag is on. It is that the precision is discarded at the read, so the analysis can express a judgement the system cannot act on — and nothing reports the loss, because from the reader's side there is nothing missing.

The frontend closes the trap. The control is a two-state Toggle whose handler is set('realBased', !f.realBased): the first click on a 0.25 writes false. The fraction survives exactly until a human touches the switch that displays it.

This also settles the open question about the prompt. No generation was needed to answer it: the tests are bare truthy, 0.25 is truthy, so the line “Based on a real story/subject; reality level = INSPIRED” is in that build's prompts by construction. A question answerable from the code should never be answered by spending a generation — the code is both cheaper and harder evidence.

The pair was safe by accident

Before the save, both builds of the controlled pair were checked through the real asSourceText(): 105,177 and 105,179 characters, both passing the first branch of :1215. So neither could fall through to intake.sourceText and regenerate against the new paste.

What makes that worth recording is the state of the field they were protected from: the shared intake_profiles.sourceText is 0 characters. Any build not carrying its own copy would today regenerate against nothing at all. The pair is safe because createBuild copies the brief verbatim — not because anything in the system knows those builds need protecting. Protection that nothing asserts is a coincidence, and a coincidence holds only until the copy it depends on stops being made.

This is the third field on the same shared row after intake.treatment and characterBible, and the first where the collision was avoided rather than survived.
